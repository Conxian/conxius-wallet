# Broad Protocol Enablement — Phased Plan

**Date:** 2026-10-03
**Status:** ACTIVE — Phases 1–4 implemented (EVM, Stacks/Liquid, Babylon/Taproot, MuSig2 native crypto); Phase 5a NWC native signing this PR
**Scope:** `conxius-wallet` — un-stub the 19 non-L1 protocol Managers and make them
reachable end-to-end from the TypeScript boundary, following the Bitcoin L1
pattern established by PR #633 (native sign + broadcast) and PR #636 (Capacitor
bridge).

---

## 1. Context

After #633 and #636, Bitcoin L1 send is reachable end-to-end from the TS layer:
`Secp256k1Signer` (BIP32/BIP84 via BDK + Bouncy Castle ECDSA) → `SecureEnclavePlugin`
(Capacitor) → `services/enclave-storage.ts` / `services/signer.ts`. The two honest
caveats that remain are (a) the Compose screens are dead code, and (b) the 19
non-L1 protocol Managers are still `ProductionRuntimeGuard.failClosed` stubs — they
return a simulated result in debug builds and throw in release builds.

"Broad enablement" means turning those stubs into real, non-custodial, evidence-gated
signing paths. It is deliberately **phased**: each protocol is enabled only when it
can reuse existing primitives or a qualified provider, has canonical test vectors,
and stays inside the neutral-rail / non-custodial boundary. It does **not** mean
shipping 19 unverified integrations at once.

## 2. Scope guardrail — live BIPs/protocols only

Enablement targets **activated and deployed** protocols. Dead or superseded
proposals are explicitly out of scope:

- **BIP-100** (dynamic maximum block size by miner vote) — never activated; **not
  implemented, not followed**.
- **BIP-110** ("Reduced Data Temporary Softfork") — a *consensus* softfork that
  temporarily limits data-field sizes (OP_RETURN ≤ 83 B, pushdata ≤ 256 B, etc.).
  It is **Closed** (2026-08-09, after a chain split with stalled mining) and was
  never active on mainnet. It is **not** a fee-estimation proposal and is **not**
  a target of this wallet. The bounded clean-block fee sampling in
  `services/bitcoin-fee-oracle.ts` is an independent client-side heuristic; see
  `docs/operations/CLEAN_BLOCK_FEE_MODEL.md` (corrected label).
- **BitVM2** — research/quarantine only; no reviewed verifier or dispute signer
  exists, so it is never auto-enabled (see the BitVM2 gate in
  `IMPLEMENTATION_REGISTRY.md`).

Live families in scope: Bitcoin/UTXO (Bitcoin, Stacks, Liquid, Babylon, BOB),
EVM (Ethereum, Base, Arbitrum, Optimism, Polygon), Cosmos/IBC, plus the
Bitcoin-native protocols with deployed tooling (Lightning/Breez, NWC/NIP-47,
MuSig2/BIP-327).

## 3. Enabling rubric

A manager is enabled when all of the following hold. The score is a rough
priority, not a gate — a manager can be high-priority but stay fail-closed until
its rubric is satisfied.

| Criterion | Question |
| :--- | :--- |
| **Leverage** | How many live chains/protocols does one signing path unlock? |
| **Crypto reuse** | Can it reuse `Secp256k1Signer` / BDK / Bouncy Castle, or does it need new primitives? |
| **Spec + vectors** | Is there a canonical, reproducible test vector (EIP, BIP, reference impl)? |
| **Sovereignty** | Does it reuse the Bitcoin root key and stay non-custodial? |
| **Dependency risk** | Does it need a new SDK / JNI / node / provider? |

## 5. Phase 1 — EVM (best option)

**Why EVM first.** One secp256k1 ECDSA + Keccak-256 + RLP signing path unlocks the
entire EVM family — Ethereum, Base, Arbitrum, Optimism, Polygon, and the
Bitcoin-native EVM L2s (BOB, RSK, B2, Botanix, Mezo). It reuses the exact same
secp256k1 primitive as Bitcoin L1, is fully specified (EIP-155, EIP-1559, EIP-2930,
EIP-712), and has canonical reference vectors. It is the highest-leverage, lowest-new-
crypto entry point for broad enablement.

**Design.** A new stateless `EvmSigner` object in `core-bitcoin`:

- `keccak256` (Bouncy Castle `KeccakDigest(256)`, pre-NIST padding — matches the TS `services/evm.ts`).
- RLP encoding (byte-string, list, integer, access-list).
- RFC-6979 ECDSA with low-S normalization and public-key recovery id (same signer as `Secp256k1Signer`).
- EIP-55 checksummed address derivation.
- `signLegacyTransaction` (EIP-155), `signEip1559Transaction` (dynamic fee), `signDigest` (EIP-712).

`EvmManager` becomes a thin stateless facade over `EvmSigner` (replacing `failClosed`),
and `SecureEnclavePlugin` exposes `evmAddress`, `evmSignTransaction`, and `evmSignDigest`
so the TS layer reaches EVM signing through the same boundary as Bitcoin L1. The TS
surface lives in `services/enclave-storage.ts` and `services/evm.ts` (which already
owns `keccak256`, EIP-712 hashing, and address helpers).

**Evidence.** Conformance against eth-account / libsecp256k1 vectors in
`EvmSignerTest`: EIP-155 legacy raw tx, EIP-1559 raw tx, EIP-712 "Mail" digest
signature, Keccak-256 of the empty string, and EIP-55 address derivation (both from
the fixed EIP-155 spec key and from the public BIP84 `abandon … about` mnemonic at
`m/44'/60'/0'/0/0`).

## 6. Phase 2 — Stacks + Liquid (Bitcoin-native L2s)

**Why Stacks + Liquid second.** Both are Bitcoin-adjacent and reuse secp256k1, so the
recoverable-ECDSA primitive from `EvmSigner` carries over with no new curve work.
Stacks (sBTC) is the flagship Bitcoin L2; Liquid is the deployed Elements sidechain.

**Stacks design.** A stateless `StacksSigner` object in `core-bitcoin`:

- `sha512256` (Bouncy Castle `SHA512tDigest(256)` — the SIP-018 transaction digest).
- `hash160` (RIPEMD160(SHA256)) over the *uncompressed* public key — SIP-005 addresses.
- c32check (SIP-005) address encoding, mainnet (`SP`) and testnet (`ST`).
- `signDigest` → 65-byte `r || s || recoveryId` (reuses `EvmSigner.sign`).

`StacksManager` becomes a thin stateless facade, and `SecureEnclavePlugin` exposes
`stacksAddress` + `stacksSignDigest` so the TS layer reaches Stacks signing through
the same boundary as L1/EVM. The TS facade is `services/stacks.ts`; the SIP-018
sighash is computed in JS (via `@stacks/transactions`), native only signs the digest.

**Liquid design.** A stateless `LiquidSigner` object in `core-bitcoin`:

- `signDigest` → `DER(r, s) || 0x01` (delegates to `Secp256k1Signer.signHash`, the same
  Elements sighash ECDSA as Bitcoin).
- `addressFromPrivateKey` → unconfidential P2WPKH bech32 (`ex`/`tex`/`ert` hrp).

`LiquidManager` is a thin facade; `SecureEnclavePlugin` exposes `liquidAddress` +
`liquidSignDigest`. The TS facade lives in `services/liquid.ts`. Confidential addresses
and output blinding (Pedersen/range proofs) stay in `liquidjs-lib` in the TS layer —
native only signs digests.

**Evidence.** `StacksSignerTest` conformance against `@stacks/transactions` (c32check
mainnet/testnet addresses, SHA512/256, and the recoverable `r||s||recoveryId`
signature for the fixed EIP-155 key). `LiquidSignerTest` conformance against
`liquidjs-lib` (P2WPKH bech32 addresses for mainnet/testnet/regtest) and RFC-6979
secp256k1 (Elements sighash DER).

## 7. Phase 3 — Babylon (Taproot) — this PR

**Why Babylon next.** Babylon v1 Bitcoin staking is composed entirely of *activated*
Bitcoin primitives: BIP-86 single-key P2TR derivation, BIP-341 taproot output-key
tweak, BIP-340 Schnorr keypath signing, and BIP-350 bech32m addressing. It introduces
the two primitives that the rest of the Bitcoin-native backlog (MuSig2, DLC adaptor
signatures, NWC event signing) all reuse — **x-only public keys** and **Schnorr
signatures** — so it is the highest-leverage remaining *crypto* step (one new signer
unlocks three later phases).

**Design.** A stateless `TaprootSigner` object in `core-bitcoin`:

- `xOnlyPublicKey` / `schnorrSign` (BIP-340, RFC-6979-style aux-rand nonce with
  Bouncy Castle `SHA256Digest` + secp256k1 point arithmetic).
- `taprootOutputKey` (BIP-341 `TapTweak` tagged-hash tweak).
- `p2trAddress` (BIP-350 bech32m over the x-only output key, witness v1).
- `BabylonManager` becomes a thin facade; `SecureEnclavePlugin` exposes `taprootAddress`
  and `schnorrSignDigest`; TS surface in `services/enclave-storage.ts` and
  `services/babylon.ts`.

**Evidence.** `TaprootSignerTest` asserts the official BIP-340 Schnorr vectors
(indices 0–3, plus the aux-rand/message edge cases) and the BIP-86 test vectors
(`abandon … about` mnemonic at `m/86'/0'/0'/0/0`, `/0/1`, `/1/0` → `bc1p5cyxn…`,
`bc1p4qhj…`, `bc1p3qkh…`), covering the full path `derive → x-only → TapTweak →
bech32m`.

Statuses below are against the BIP registry at bips.dev (checked 2026-10-03) and the
enabling rubric in §3. Only **activated/final** specs are enableable; **draft** specs
keep the manager fail-closed.

| :--- | :--- | :--- | :--- | :--- | :--- |

**Sequencing implication.** MuSig2 (BIP-327) is done. NWC event signing (NIP-01),
DLC adaptor signatures (Schnorr pre-signature + completion/secret-extraction), and
Lightning BOLT-11 invoice signing (compact ECDSA with recovery) are now enabled
natively — all three reuse the Phase-3 BIP-340 Schnorr / secp256k1 path with zero
new dependency surface. What remains provider-gated for each is the *transport or
oracle* layer, not the signing: NWC's relay (NIP-04/44 + a Nostr relay), DLC's CET
construction + oracle attestation, and Lightning's channel/payment routing
(Breez/LDK). Ark stays quarantined behind fail-closed because its covenant opcode
(CTV/BIP-119) is still a draft and therefore violates the "live BIPs only"
guardrail — exactly the same reason BIP-100 is excluded.
