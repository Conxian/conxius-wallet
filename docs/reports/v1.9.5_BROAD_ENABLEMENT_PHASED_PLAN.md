# Broad Protocol Enablement — Phased Plan

**Date:** 2026-10-03
**Status:** ACTIVE — Phase 1 (EVM) implemented
**Scope:** `conxius-wallet` — un-stub the 19 non-L1 protocol Managers and make them
reachable end-to-end from the TypeScript boundary, following the Bitcoin L1
pattern established by PR #633 (native sign + broadcast) and PR #636 (Capacitor
bridge).

---

## 1. Context

After #633 and #636, Bitcoin L1 send is reachable end-to-end from the TS layer:
`Secp256k1Signer` (BIP32/BIP84 via BDK + Bouncy Castle ECDSA) → `SecureEnclavePlugin`
(Capacitor) → `services/enclave-storage.ts` / `services/signer.ts`. The two honest
caveats that remain are (a) the Compose screens are dead code, and (b) the 19
non-L1 protocol Managers are still `ProductionRuntimeGuard.failClosed` stubs — they
return a simulated result in debug builds and throw in release builds.

"Broad enablement" means turning those stubs into real, non-custodial, evidence-gated
signing paths. It is deliberately **phased**: each protocol is enabled only when it
can reuse existing primitives or a qualified provider, has canonical test vectors,
and stays inside the neutral-rail / non-custodial boundary. It does **not** mean
shipping 19 unverified integrations at once.

## 2. Scope guardrail — live BIPs/protocols only

Enablement targets **activated and deployed** protocols. Dead or superseded
proposals are explicitly out of scope:

- **BIP-100** (dynamic maximum block size by miner vote) — never activated; **not
  implemented, not followed**.
- **BIP-110** (Merkelized Abstract Syntax Tree) — superseded by Taproot (BIP-341).
  Kept only as client-side fee *policy* (bounded mempool sampling), never as a
  consensus claim. See `docs/operations/BIP110_COMPLIANCE.md`.
- **BitVM2** — research/quarantine only; no reviewed verifier or dispute signer
  exists, so it is never auto-enabled (see the BitVM2 gate in
  `IMPLEMENTATION_REGISTRY.md`).

Live families in scope: Bitcoin/UTXO (Bitcoin, Stacks, Liquid, Babylon, BOB),
EVM (Ethereum, Base, Arbitrum, Optimism, Polygon), Cosmos/IBC, plus the
Bitcoin-native protocols with deployed tooling (Lightning/Breez, NWC/NIP-47,
MuSig2/BIP-327).

## 3. Enabling rubric

A manager is enabled when all of the following hold. The score is a rough
priority, not a gate — a manager can be high-priority but stay fail-closed until
its rubric is satisfied.

| Criterion | Question |
| :--- | :--- |
| **Leverage** | How many live chains/protocols does one signing path unlock? |
| **Crypto reuse** | Can it reuse `Secp256k1Signer` / BDK / Bouncy Castle, or does it need new primitives? |
| **Spec + vectors** | Is there a canonical, reproducible test vector (EIP, BIP, reference impl)? |
| **Sovereignty** | Does it reuse the Bitcoin root key and stay non-custodial? |
| **Dependency risk** | Does it need a new SDK / JNI / node / provider? |

## 5. Phase 1 — EVM (best option)

**Why EVM first.** One secp256k1 ECDSA + Keccak-256 + RLP signing path unlocks the
entire EVM family — Ethereum, Base, Arbitrum, Optimism, Polygon, and the
Bitcoin-native EVM L2s (BOB, RSK, B2, Botanix, Mezo). It reuses the exact same
secp256k1 primitive as Bitcoin L1, is fully specified (EIP-155, EIP-1559, EIP-2930,
EIP-712), and has canonical reference vectors. It is the highest-leverage, lowest-new-
crypto entry point for broad enablement.

**Design.** A new stateless `EvmSigner` object in `core-bitcoin`:

- `keccak256` (Bouncy Castle `KeccakDigest(256)`, pre-NIST padding — matches the TS `services/evm.ts`).
- RLP encoding (byte-string, list, integer, access-list).
- RFC-6979 ECDSA with low-S normalization and public-key recovery id (same signer as `Secp256k1Signer`).
- EIP-55 checksummed address derivation.
- `signLegacyTransaction` (EIP-155), `signEip1559Transaction` (dynamic fee), `signDigest` (EIP-712).

`EvmManager` becomes a thin stateless facade over `EvmSigner` (replacing `failClosed`),
and `SecureEnclavePlugin` exposes `evmAddress`, `evmSignTransaction`, and `evmSignDigest`
so the TS layer reaches EVM signing through the same boundary as Bitcoin L1. The TS
surface lives in `services/enclave-storage.ts` and `services/evm.ts` (which already
owns `keccak256`, EIP-712 hashing, and address helpers).

**Evidence.** Conformance against eth-account / libsecp256k1 vectors in
`EvmSignerTest`: EIP-155 legacy raw tx, EIP-1559 raw tx, EIP-712 "Mail" digest
signature, Keccak-256 of the empty string, and EIP-55 address derivation (both from
the fixed EIP-155 spec key and from the public BIP84 `abandon … about` mnemonic at
`m/44'/60'/0'/0/0`).

## 6. Subsequent phases (preview)

- **Stacks**: `signStacksTransaction` is ECDSA over a SIP-018 hashed payload — reuses
  `Secp256k1Signer`; needs the Stacks transaction serialization + post-condition
  hashing (canonical vectors from the Stacks reference client).
- **Liquid**: confidential transactions (Pedersen commitments, range proofs, blinding)
  are the hard part; port the elements-lib blinding path behind `ProductionRuntimeGuard`.
- **Babylon**: Taproot staking is BIP-86 — BDK already supports Taproot descriptors.
- **MuSig2**: BIP-327 two-round nonce/partial/aggregate — well-specified; needs a
  session-state wrapper around secp256k1.
- **Lightning/NWC**: Breez SDK or LDK node management + NIP-47 event signing (secp256k1
  Schnorr). Provider-gated.
- **Long-tail**: each requires a *qualified* provider/SDK and reproducible evidence
  before it leaves fail-closed (same discipline as the value-operation gate in
  `IMPLEMENTATION_REGISTRY.md`).
